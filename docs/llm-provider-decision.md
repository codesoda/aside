# Optional review-analysis LLM provider decision

**Decision date:** 23 November 2026 (AEST). **Status:** deferred; default off. **Scope:** [#39](https://github.com/codesoda/aside/issues/39#issuecomment-7086172699), the gate for proposed [#42](https://github.com/codesoda/aside/issues/42). This record is not approval to transmit source code or implement a provider.

## Present behavior and decision

The default review-analysis registry runs bounded, non-LLM diff and Git-history analysis. Initial analysis and Refresh do not select an LLM provider by default; a partial history result is still legitimate, not evidence of model use. Existing **Explain** is a separate, explicit, on-demand question-and-answer feature: a configured local Ollama model can answer locally, and a deliberately enabled Claude CLI can answer through the unmodified installed CLI. Default Explain configuration has no local model and disables Claude; discovery does not invoke a model. Unconfigured hosted requests are rejected. Codex Explain is listed but unavailable. Do not describe Aside as having no LLM integration, or describe these exercised defaults as a universal network-egress guarantee: GitHub ingestion and explicitly authorized history fetches have separate network behavior. See [analysis configuration](analysis-configuration.md) for current controls; those settings do not enable model analysis.

**Defer optional review-analysis LLM candidates to #42 and keep them off by default.** A user-funded API-key adapter is the conditional first avenue to evaluate, not a committed provider selection or permission to call an API. An existing key, subscription, authenticated CLI, or Explain setting does not authorize review-analysis uploads. No automatic migration from subscription allowance to metered API billing, credential extraction, or silent fallback is acceptable. #42 needs an explicit approval decision and evidence that the contract below is implemented and tested before enabling outbound analysis.

## Required contract before any future enabled mode

1. **Separate explicit consent per host-qualified repository and provider.** Default remains disabled, including on first open and Refresh. Show the chosen mode and obtain affirmative approval before the first transmission. Record consent scope, version and time locally; provide revocation and require fresh consent when provider, endpoint, auth/billing route, material payload scope or privacy terms change. Credentials and prior Explain consent never imply review-analysis consent. Lack of approval fails closed.
2. **Preview and disclose before sending.** Show repository and the full, inspectable, exact outgoing request payload, including all selected diff/context content, prompts and transmitted metadata after redaction, not a representative sample or only path names. Show its size, provider/model, destination endpoint, authentication route and account/billing mode, applicable privacy/retention links, expected request count and budget. Bind approval to that exact payload and destination; a regenerated or changed payload requires a new preview and approval before dispatch. Make clear that code, comments, metadata and secrets may reach a third party; disclose separately any local model and whether its configured endpoint is truly local. Do not hide a hosted endpoint behind a “local” label.
3. **Minimize and bound the payload.** Select only required changed hunks and justified neighboring context; never send whole-repository content by default. Exclude unrelated files and sensitive metadata; provide reviewable redaction and an opportunity to remove material. Secret detection/redaction is best-effort and cannot prove payloads contain no secrets. Do not log raw prompts/source or submit provider feedback automatically. Fail closed on any mismatch between the approved preview and the exact outgoing payload, context or metadata; regenerate the preview and seek renewed approval rather than allowing a “material” divergence.
4. **Enforce limits before dispatch and during execution.** Set hard per-run maxima for input bytes/tokens, output tokens, requests (including validation passes), retries, concurrency and wall-clock time. Count retries and cache misses against limits; stop on exhaustion or cancellation, and avoid unbounded automatic reruns on Refresh. Disable paid tools, external fetches and autonomous tool execution unless separately approved. Rate limits alone are not spending limits.
5. **Make billing honest.** For a priced API route, calculate a conservative ceiling from current model/endpoint prices, maximum input/output and all billable requests, retries, cache/tool and feature charges; show currency, source/date, assumptions and the cap before approval. Abort if a reliable ceiling cannot be computed rather than promise a hard monetary guarantee. For subscription plans, dynamic rates, credits or unknown charges, show **unknown cost/allowance impact**, require a distinct acknowledgement, and enforce strict nonmonetary caps; never display unknown as $0. Provider-side budgets are not a substitute for local limits. Exhausted quota must not silently switch provider, model, auth route or paid API mode.
6. **Keep review authority separate.** Label model output as attributed, uncertain suggestions tied to snapshot and context; validate anchors and stale results. Only promote candidates to local editable drafts through a separate action. Model analysis cannot mark files reviewed, approve, publish comments or change GitHub state. Consent to transmission does not authorize code execution or publication.

**Approval gate for #42:** maintainers must explicitly approve the provider/auth route and disclosure/budget design after checking current official terms and account eligibility; tests must demonstrate credential-present and credential-absent default paths make zero model invocations, while preserving explicitly configured Explain behavior, and demonstrate consent denial, payload/limit enforcement and failure handling for any new adapter. Default-path tests do not establish a universal no-network audit. Until then this is a decision record, not an enabled feature.
